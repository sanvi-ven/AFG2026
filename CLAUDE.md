# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Anchor" (repo/GitHub name `AFG2026`) is a small-business field-service CRM: appointments, estimates, invoices, jobs/scheduling, equipment tracking, client/employee messaging. It's currently being run for the user's landscaping business, but nothing in the code is landscaping-specific — business branding (company name, address, logo, PDF filename templates) is configurable per-tenant via Owner Settings.

Stack: Flutter frontend (`frontend/`) + FastAPI backend (`backend/`). The frontend is backed directly by the `afg2026a` Firebase project (Firestore + Firebase Auth), deployed via Vercel (`vercel.json` + `build.sh`) at `anchor-orpin.vercel.app`. The backend is a **separate GCP project** (`project-d977b7e6-dcb5-4209-aa0`, "My First Project") running Cloud Run service `anchor-backend` in `us-central1` — see "Deployment & secrets" below, this split matters for anyone trying to find/deploy the backend.

**Read this whole file before making auth/security changes** — the auth model has real, verified identity and real, role-scoped Firestore rules now (as of 2026-09-01), but the migration was deliberately scoped (see "Auth model" below) and one thing that would be true in a "normal" Firebase app still isn't true here: the backend has almost no auth-gated routes (`/comms/*`, `/photos/upload`).

## Commands

### Frontend (Flutter, from `frontend/`)
```bash
flutter pub get
flutter run -d chrome --dart-define=API_BASE_URL=http://127.0.0.1:8000   # run against local backend
flutter analyze                                                          # lint (flutter_lints)
flutter test                                                             # runs frontend/test/widget_test.dart (only test in the repo)
flutter test test/widget_test.dart                                      # single test file
flutter build web --release --dart-define=API_BASE_URL=<url>            # production web build (what build.sh does)
```
Useful `--dart-define` flags read by `frontend/lib/core/config/app_config.dart`:
- `API_BASE_URL` — FastAPI base URL (default `http://127.0.0.1:8000`)
- `DEMO_ROLE` — `owner`/`client`/`employee`; when set, `AnchorApp` skips login entirely and opens `DashboardPage` directly with a fake `dev-*` token. **This bypasses the real Firebase Auth session entirely** (no real `uid`, no custom claim) — fine for quickly poking at UI that doesn't depend on `ClientSession`/`EmployeeSession` having a real profile loaded, but anything that reads the signed-in user's own Firestore doc (settings dialogs, `fetchByUid`, etc.) won't have one. For anything auth-related, sign in for real instead.
- `DEMO_AUTH_TOKEN` — override the fake token sent alongside `DEMO_ROLE`

### Backend (FastAPI, from `backend/`)
```bash
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
cp .env.example .env               # then fill in as needed; USE_MOCK_FIRESTORE=true + DEV_AUTH_BYPASS=true works with no Firebase creds at all
uvicorn app.main:app --reload --port 8000
```
There are no backend tests in the repo. `.env` and `service-account.json` are gitignored — never commit or print their contents.

### Deploy
- Frontend: pushing to `main` triggers Vercel, which runs `bash build.sh` (root or `frontend/vercel.json`) and serves `frontend/build/web` at `anchor-orpin.vercel.app`.
- Firestore rules: `firebase deploy --only firestore:rules --project afg2026a`. Storage rules (`storage.rules`) are registered in `firebase.json` too, but **Firebase Storage is not actually provisioned on this project** (zero buckets exist, confirmed via `gcloud storage buckets list --project afg2026a`) — `firebase deploy --only storage` will fail until/unless Storage is set up via the Firebase console. The rules file is kept up to date anyway in case that ever changes; don't assume it's live.
- Backend: **not on Vercel** — it's Cloud Run service `anchor-backend` in GCP project `project-d977b7e6-dcb5-4209-aa0`, region `us-central1`, deployed from the `backend/Dockerfile`. Deploy with:

  `immc17289@gmail.com` has `roles/owner` on that GCP project (and is also the Firebase project's owner, and the account behind the `firebase-tools`/`gcloud` CLI logins noted in memory) — that's the account to deploy as. ### Secrets (backend, on Cloud Run)
As of 2026-09-01, the credential-shaped env vars (`RESEND_API_KEY`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `GOOGLE_SERVICE_ACCOUNT_JSON_BASE64`) live in **Google Secret Manager** on the backend's GCP project (`project-d977b7e6-dcb5-4209-aa0`), not as plaintext Cloud Run env vars — secret names match the env var name in kebab-case (e.g. `RESEND_API_KEY` → secret `resend-api-key`). The Cloud Run runtime service account (`1001439279043-compute@developer.gserviceaccount.com`) has `roles/secretmanager.secretAccessor` on each. Non-secret config (`FIREBASE_PROJECT_ID`, `USE_MOCK_FIRESTORE`, `DEV_AUTH_BYPASS`, `RESEND_FROM_EMAIL`, `CLOUDINARY_CLOUD_NAME`, `TWILIO_FROM_NUMBER`, `ALLOWED_ORIGINS_RAW`) stays as plain env vars. A redeploy that changes code but not config should pass `--update-secrets`/`--set-env-vars` again (or copy them from the current revision) — `gcloud run deploy --source ...` without those flags will **not** carry them forward automatically on a source-only deploy in all cases; verify with:
```bash
gcloud run services describe anchor-backend --region us-central1 --project project-d977b7e6-dcb5-4209-aa0 --format="value(spec.template.spec.containers[0].env.list())"
```
This should show `valueFrom.secretKeyRef` for the six credential vars, never a raw value — if it ever shows a plaintext value for one of those six, that's a regression of the 2026-09-01 Secret Manager migration.

## Architecture

### Two parallel data-access paths — know which one a feature actually uses
This is the single most important thing to understand before touching a feature. There are two completely separate ways the frontend reaches data, and most features use only one:

1. **Direct Flutter ↔ Firestore** (`package:cloud_firestore`), via `*_service.dart` files in `frontend/lib/core/services/` (e.g. `client_profile_service.dart`, `invoice_service.dart`, `estimate_service.dart`, `scheduled_work_service.dart`, `equipment_service.dart`, `team_service.dart`, `time_entry_service.dart`, `message_service.dart`, `notification_service.dart`, `owner_settings_service.dart`, etc.). This is how essentially **all** real feature pages read/write data today — clients, jobs, invoices, estimates, equipment, employees, teams, time tracking, expenses, notifications, in-app messages, requests, service catalog, checklists.
2. **FastAPI backend via `ApiClient`** (`frontend/lib/core/services/api_client.dart`, plain `http` calls to `$API_BASE_URL/api/v1/...`). In the current frontend this is only actually wired up for `CommsService` (transactional email/SMS via `/comms`, which holds Resend/Twilio keys server-side) and photo upload (`job_photo_upload_service.dart` → `/photos/upload`, which holds the Cloudinary secret server-side).

As of 2026-09-01, the backend **only implements what's actually reachable**: `auth` (`/auth/complete-signup`, `/auth/claim-account` — see Auth model below), `comms` (`/comms/email`, `/comms/sms`), and `photos` (`/photos/upload`). A large REST+Firestore-repository CRUD layer for appointments/invoices/messages/notifications/users, a Google Calendar booking API, the old `/auth/google` route, and a second (bcrypt-based, `core/security.py`) client-auth implementation used to exist here — all confirmed unreachable from the shipped frontend (it talks to differently-named Firestore collections directly instead, e.g. jobs live in `scheduled_work` via `scheduled_work_service.dart`, not the old `appointments` route) — and were deleted rather than secured, since securing dead code has no payoff. `docs/ARCHITECTURE.md` and `docs/technical/PROJECT_MAP.md` describe that earlier, more backend-centric design and are now doubly stale — don't trust them as current. When asked to change how a feature reads/writes data, `grep` that feature's `presentation/*.dart` file's imports first to see which of the two paths it's actually on.

### Auth model — real identity, real Firestore rules, for all three roles
**As of 2026-09-01, all three roles use real Firebase Auth, and `firestore.rules` actually enforces role- and identity-scoped access on every collection** (previously: hardcoded owner password, client/employee SHA-256-in-Firestore, and `allow read, write: if true` almost everywhere). Read this before touching login, signup, any `*_service.dart` query/write, or `firestore.rules`:

- **Identity**: a Firebase Auth account per user (email/password for all three roles — no Google Sign-In in the live app, `FirebaseService`/`google_sign_in` are unused). Two **custom claims** are the source of truth, set *only* server-side, never trust a client-supplied value:
  - `role` (`owner`/`employee`/`client`) — what someone is.
  - `profile_id` (client/employee only) — the caller's own `client_signups`/`employee_signups` **doc id**. This exists because those two collections are the only ones with a real `uid` field; every other collection (`estimates`, `invoices`, `scheduled_work`, `client_messages`, `notifications`, `time_entries`, `employee_availability`, …) identifies "whose record is this" by that old doc id, not `uid` — `firestore.rules` compares `resource.data.clientId`/`employeeId` against `request.auth.token.profile_id` to scope a session to its own records, rather than requiring a data migration of every document to store `uid` instead.
- **Who can become what**: `POST /auth/complete-signup` (`backend/app/api/v1/routes/auth.py`) is the only place a role (and `profile_id`) gets granted, given an already-verified Firebase ID token. `owner` requires the caller's email to be in `settings.owner_emails` (`OWNER_EMAILS_RAW` env var, currently just `immc17289@gmail.com`, and gets no `profile_id` — owner-only rules just check `role`); `employee` requires a real `invite_codes` entry; `client` is unconditional. `POST /auth/claim-account` is the separate pre-auth flow for turning an owner-created "dummy" client (`ClientProfileService.createDummyClient`, no email/password yet) into a real login via a one-time claim code — it creates the Firebase user itself since no one is signed in yet at that point.
- **Frontend**: `login_page.dart`/`owner_signin_page.dart` use `FirebaseAuth.instance.signIn/createUserWithEmailAndPassword` directly; the app's real entry point is `_SessionGate` in `frontend/lib/app.dart`, which now reacts to `FirebaseAuth.instance.authStateChanges()` (reading the `role` claim off a fresh ID token, then loading the matching profile) instead of a local-storage session blob — `SessionPersistenceService` is gone, Firebase's own SDK persistence replaced it. `ClientProfileService.fetchByUid`/`EmployeeProfileService.fetchByUid` (query by a `uid` field, not the doc ID — existing docs keep their old IDs, only new field added) are how a profile gets resolved from a signed-in Firebase user. `client_signup_page.dart`/`employee_signup_page.dart` force a **second** `getIdToken(true)` refresh after `/auth/complete-signup` returns, before navigating to the dashboard — the first token (fetched pre-signup) predates the claims `/auth/complete-signup` just set, and reusing it caused one `permission-denied` on the very first dashboard load. A similar, less deterministic token-propagation lag was observed once on an ordinary (non-signup) employee login too, self-resolving on retry — not yet root-caused or fixed; if it recurs, look at Firestore Web SDK auth-state propagation, not the rules themselves.
- **Migration** (one-off, already run against production): `backend/scripts/migrate_existing_accounts.py` created a Firebase Auth account + `role` claim for every pre-existing `client_signups`/`employee_signups` doc that had a real `password_hash` (dummy/unclaimed clients were left untouched — they still go through claim-account), stripped `password_hash`, and generated (but didn't send) a password-reset link per account; `backend/scripts/send_reset_emails.py` is the separate, deliberately-manual step that actually emails those links. `backend/scripts/backfill_profile_id_claims.py` (also one-off, already run) is the equivalent backfill for the `profile_id` claim — needed once, since accounts migrated before `profile_id` existed only had `role` set.

**`firestore.rules` design** (see the file itself for the exact per-collection logic): owner gets unrestricted access everywhere. Client/employee-scoped collections (`estimates`, `invoices`, `scheduled_work`, `client_messages`, `notifications`) check `resource.data.clientId`/`targetClientId`/`recipientId` against the caller's `profile_id` claim; a client can additionally write `status`/`changeRequestMessage` on their own estimate (approve / request changes — the only writes the client UI performs) but nothing else. `time_entries`/`employee_availability` are employee-self-scoped by `profile_id` too (new write-integrity protection — previously nothing stopped one employee's session from editing another's hours or availability). `equipment`/`equipment_reservations`/`broken_reports`/`service_records`/`job_completion_forms`/`teams` are staff-shared (owner + employee, no per-employee scoping — this codifies the app's existing "full parity" design, not a new restriction). `expenses`/`service_catalog`/`checklist_templates`/`invite_codes` are owner-only. `owner_settings` stays publicly readable (branding is used on the pre-auth lead form and on both owner- and client-facing PDFs) but owner-only to write. `requests` allows public `create` (the pre-auth "Request a Quote" form) but staff-only read/update. Because several pages (`messages_page.dart`, `estimates_page.dart`, `invoices_page.dart`, `appointments_page.dart`) used to call `ClientProfileService.watchAllProfiles()` (the full, unscoped client directory) unconditionally regardless of role just to resolve a display name, those call sites were changed to skip that subscription (or substitute the caller's own already-known profile) for client-role sessions; `dashboard_page.dart`'s `ReminderCheckService.checkAndCreateReminders()` call — inherently business-wide (scans every client's invoices/appointments) — is now gated to `role == 'owner'` only instead of firing for every role on every dashboard load.

**What's still NOT covered** — don't assume otherwise:
- Backend routes still aren't auth-gated. `get_current_user`/`require_owner` in `backend/app/api/deps/auth.py` work correctly against real tokens now (and `/auth/complete-signup` uses the same verification), but `/comms/*` and `/photos/upload` still take no `Authorization` header at all — they're only IP-rate-limited (Phase 0), not authenticated. Wiring them through `get_current_user` is a small, separate follow-up, not yet done.
- `DEV_AUTH_BYPASS` (`dev-owner`/`dev-employee`/`dev-client` fake tokens, `deps/auth.py`) still exists for local/mock-Firestore dev and is guarded by the Phase 0 startup check (`core/config.py`) — it's unrelated to the real auth system and never touches it.

### Backend layering
Standard layered FastAPI structure: `api/v1/routes/*.py` (request/response, now just `auth.py`/`comms.py`/`photos.py`) → `services/*.py` (business logic) → `repositories/firestore_repository.py` (generic Firestore CRUD, with an in-memory dict fallback when `USE_MOCK_FIRESTORE=true`, used only by `users_service.py` today) → `schemas/*.py` (pydantic models). `core/config.py` (`Settings`, env-driven, see Auth model above for the dev-bypass guard), `core/firebase.py` (lazy Firebase Admin init, supports both a checked-in `service-account.json` and a base64 env var for Cloud Run), and `core/rate_limit.py` (the shared `slowapi` `Limiter` instance) are shared across routes.

### Frontend layering
`lib/features/<feature>/presentation/*.dart` (pages/widgets) → `lib/core/services/*.dart` (data access — Firestore directly or `ApiClient`, per feature) → `lib/models/*.dart` (plain Dart model classes with `fromMap`/`toMap`/`fromJson`). Routing is a single `switch` in `lib/core/router/app_router.dart` (`AppRouter.onGenerateRoute`); role and `authToken` are passed as route arguments (a `Map<String, dynamic>`) on every in-app navigation call, so an individual page's "current role" is whatever the caller happened to pass — `_SessionGate` (see Auth model) is the one place that derives role from the real, global Firebase Auth state (on app boot / auth state change), then threads it into the first route args the same way. Global mutable session state (`ClientSession`, `EmployeeSession`, `OwnerSession` in `lib/core/state/`) is `ValueNotifier`-based and used for cross-cutting concerns like the notification listeners in `app.dart`, separate from the per-route role/token arguments.

Platform-conditional code (CSV/PDF download, Google Calendar embedding) is split into `_io.dart`/`_web.dart`/`_stub.dart` variants per service (e.g. `csv_download_service_web.dart` vs `_io.dart`) selected via conditional imports from the non-suffixed file — follow that pattern for anything else that needs to behave differently on web vs. native.
