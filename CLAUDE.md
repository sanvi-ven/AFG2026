# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Anchor" (repo/GitHub name `AFG2026`) is a small-business field-service CRM: appointments, estimates, invoices, jobs/scheduling, equipment tracking, client/employee messaging. It's currently being run for the user's landscaping business, but nothing in the code is landscaping-specific — business branding (company name, address, logo, PDF filename templates) is configurable per-tenant via Owner Settings.

Stack: Flutter frontend (`frontend/`) + FastAPI backend (`backend/`). The frontend is backed directly by the `afg2026a` Firebase project (Firestore + Firebase Auth), deployed via Vercel (`vercel.json` + `build.sh`) at `anchor-orpin.vercel.app`. The backend is a **separate GCP project** (`project-d977b7e6-dcb5-4209-aa0`, "My First Project") running Cloud Run service `anchor-backend` in `us-central1` — see "Deployment & secrets" below, this split matters for anyone trying to find/deploy the backend.

**Read this whole file before making auth/security changes** — the auth model has real, verified identity and real, role-scoped Firestore rules now (as of 2026-09-01), and `/comms/*`/`/photos/upload` are auth-gated too, except for the two specific pre-auth cases the public "Request a Quote" form genuinely needs (see "Comms & photos" under Auth model below) — don't assume either backend route is either "fully open" or "fully auth-required," it's neither.

## Commands

### Frontend (Flutter, from `frontend/`)
```bash
flutter pub get
flutter run -d chrome --dart-define=API_BASE_URL=http://127.0.0.1:8000   # run against local backend
flutter analyze                                                          # lint (flutter_lints)
flutter test                                                             # runs frontend/test/widget_test.dart (only test in the repo)
flutter test test/widget_test.dart                                      # single test file
flutter build web --release --dart-define=API_BASE_URL=<url>            # production web build (what build.sh does)
```
Useful `--dart-define` flags read by `frontend/lib/core/config/app_config.dart`:
- `API_BASE_URL` — FastAPI base URL (default `http://127.0.0.1:8000`)
- `DEMO_ROLE` — `owner`/`client`/`employee`; when set, `AnchorApp` skips login entirely and opens `DashboardPage` directly with a fake `dev-*` token. **This bypasses the real Firebase Auth session entirely** (no real `uid`, no custom claim) — fine for quickly poking at UI that doesn't depend on `ClientSession`/`EmployeeSession` having a real profile loaded, but anything that reads the signed-in user's own Firestore doc (settings dialogs, `fetchByUid`, etc.) won't have one. For anything auth-related, sign in for real instead.
- `DEMO_AUTH_TOKEN` — override the fake token sent alongside `DEMO_ROLE`

### Backend (FastAPI, from `backend/`)
```bash
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
cp .env.example .env               # then fill in as needed; USE_MOCK_FIRESTORE=true + DEV_AUTH_BYPASS=true works with no Firebase creds at all
uvicorn app.main:app --reload --port 8000
```
There are no backend tests in the repo. `.env` and `service-account.json` are gitignored — never commit or print their contents.


### Firebase project settings (live config, not in repo files)
Set once via direct API/CLI calls (`gcloud`/Identity Toolkit Admin API), documented here so a future session doesn't have to rediscover them by querying the live project again:
- **Password policy**: `passwordPolicyConfig` on the `afg2026a` Identity Toolkit config is `ENFORCE`d with `minPasswordLength: 8`, matching the signup forms' own client-side check — Firebase's bare default (6 chars, no policy) previously meant that check was cosmetic, bypassable via a direct API call. Query with `curl -H "Authorization: Bearer $(gcloud auth print-access-token)" -H "x-goog-user-project: afg2026a" https://identitytoolkit.googleapis.com/admin/v2/projects/afg2026a/config`.
- **Browser API key restriction**: the Firebase Web SDK's public API key (`frontend/lib/firebase_options.dart`) has an `allowedReferrers` restriction (`gcloud services api-keys update --allowed-referrers=...`) scoped to `anchor-orpin.vercel.app` and `localhost`/`127.0.0.1` — it had none before. This is defense-in-depth against quota/billing abuse from other sites embedding the key (it can't bypass Firestore rules either way); check with `gcloud services api-keys list --project=afg2026a`. **Pattern syntax gotcha, confirmed the hard way**: despite `gcloud`'s own `--help` text calling these "regular expressions," actual enforcement does *not* accept true regex (a `https://anchor-orpin\.vercel\.app/.*` pattern was accepted by `gcloud` at write time but silently rejected every real request, including from the real production site, until corrected) — use the plain glob form Google Cloud Console itself would generate instead, e.g. `https://anchor-orpin.vercel.app/*`, `http://localhost:*/*`. After changing this restriction, verify it against a live request (not just that `gcloud` accepted the update) before considering the change done.
- **Firestore delete protection**: `deleteProtectionState: DELETE_PROTECTION_ENABLED` on the `(default)` database (`gcloud firestore databases update --delete-protection`) — prevents an accidental/malicious full-database delete. Point-in-time recovery is still **disabled** (small ongoing storage cost, deliberately left as an opt-in the user hasn't taken yet, not an oversight).

## Architecture

### Two parallel data-access paths — know which one a feature actually uses
This is the single most important thing to understand before touching a feature. There are two completely separate ways the frontend reaches data, and most features use only one:

1. **Direct Flutter ↔ Firestore** (`package:cloud_firestore`), via `*_service.dart` files in `frontend/lib/core/services/` (e.g. `client_profile_service.dart`, `invoice_service.dart`, `estimate_service.dart`, `scheduled_work_service.dart`, `equipment_service.dart`, `equipment_reservation_service.dart`, `equipment_basket_service.dart`, `equipment_kit_service.dart`, `team_service.dart`, `time_entry_service.dart`, `message_service.dart`, `notification_service.dart`, `owner_settings_service.dart`, etc.). This is how essentially **all** real feature pages read/write data today — clients, jobs, invoices, estimates, equipment, employees, teams, time tracking, expenses, notifications, in-app messages, requests, service catalog, checklists.
2. **FastAPI backend via `ApiClient`** (`frontend/lib/core/services/api_client.dart`, plain `http` calls to `$API_BASE_URL/api/v1/...`). In the current frontend this is only actually wired up for `CommsService` (transactional email/SMS via `/comms`, which holds Resend/Twilio keys server-side) and photo upload (`job_photo_upload_service.dart` → `/photos/upload`, which holds the Cloudinary secret server-side).

As of 2026-09-01, the backend **only implements what's actually reachable**: `auth` (`/auth/complete-signup`, `/auth/claim-account` — see Auth model below), `comms` (`/comms/email`, `/comms/sms`), and `photos` (`/photos/upload`). A large REST+Firestore-repository CRUD layer for appointments/invoices/messages/notifications/users, a Google Calendar booking API, the old `/auth/google` route, a second (bcrypt-based, `core/security.py`) client-auth implementation, and `api/deps/auth.py`'s `get_current_user`/`require_owner` (unused once `/comms`/`/photos` grew their own local, self-contained auth checks instead of reusing that layer) all used to exist here — all confirmed unreachable from the shipped frontend (it talks to differently-named Firestore collections directly instead, e.g. jobs live in `scheduled_work` via `scheduled_work_service.dart`, not the old `appointments` route) — and were deleted rather than secured/kept, since dead code has no payoff either way. `docs/ARCHITECTURE.md` and `docs/technical/PROJECT_MAP.md`, which described that earlier backend-centric design, were deleted for the same reason (they'd gone doubly stale). When asked to change how a feature reads/writes data, `grep` that feature's `presentation/*.dart` file's imports first to see which of the two paths it's actually on.

### Equipment baskets and kits (added 2026-09-01)
A basket (`equipment_baskets`, `equipment_basket_service.dart`, model `equipment_basket.dart`) lets staff reserve a set of equipment + supplies for one shared time window and check it all out / return it all at once, instead of one item at a time. The equipment side is still one `EquipmentReservation` doc per unit — unchanged from the original single-item flow — just tagged with a new optional `EquipmentReservation.basketId` field (empty on every reservation created before this feature, and on any reservation still created via the equipment detail page's standalone "Request equipment" quick-reserve, which was deliberately left untouched). `EquipmentBasketService.checkOutBasket`/`returnBasket` batch-stamp every reservation in the basket at once, while `EquipmentBasketCard` (the shared display widget used by the owner schedule tab, "My Equipment", and the job detail page) also exposes a per-item check-out/return so one item coming back early doesn't block the rest. Supplies have no per-unit or time-conflict concept, so they're embedded directly on the basket doc as `supplyLines` (`EquipmentBasketSupplyLine`) rather than getting their own reservation docs; the actual stock decrement (`EquipmentItem.quantity`) happens at basket check-out, not at basket creation, so two pending baskets can't both silently "reserve" the same units of stock. A basket's status is always derived from its live children (`EquipmentBasket.computeStatus`) rather than stored, so it can't drift out of sync.

A kit (`equipment_kits`, `equipment_kit_service.dart`, model `equipment_kit.dart`) is a saved, reusable preset list (e.g. "Mowing setup") that pre-fills a basket's item list — picking one is a starting point, not a lock; every quantity/item stays editable afterward. Kits are staff-shared with no creator-only edit restriction (any owner or employee can edit/delete any kit), matching this app's existing equipment/teams "full parity" design rather than the owner-only pattern used by `service_catalog`/`checklist_templates` — `createdByName` is display-only attribution, preserved across edits by other staff, not a permission check.

### Legal documents: Privacy Policy, Terms of Service, Employee Data Privacy Notice (added 2026-09-01)
Three documents — `privacy_policy`, `terms_of_service`, `employee_data_notice` (fixed IDs in `LegalDocumentIds`) — live as editable Firestore docs in the `legal_documents` collection (model `legal_document.dart`, service `legal_document_service.dart`), not hardcoded in the app, so the owner can update wording (e.g. contact info, policy changes) from **Owner Settings → Manage Legal Documents** (`legal_documents_admin_page.dart`) without a code deploy. Content is plain text with a tiny in-house markup — `# ` title, `## ` section heading, `- ` bullet, `**text**` bold, blank line = new paragraph — parsed by `LegalDocumentBody` in `legal_document_page.dart` (bold is rendered via `_parseInlineBold`'s own `**...**` regex split into `TextSpan`s, applied inside both the paragraph and bullet branches; a first pass shipped without this and the seeded content's `**label:**` lead-ins showed up as literal asterisks on the live page until caught by actually loading it). Deliberately not real markdown — this app has no markdown package dependency. `docs/legal/*.txt` are the source-of-truth drafts the collection was originally seeded from (`backend/scripts/seed_legal_documents.py`, safe to re-run to reset a document, but will overwrite any edits the owner made in-app since) — keep them in sync manually if you want the checked-in copies to reflect real in-app edits; the app never reads these files directly. `legal_documents` is publicly readable (`allow read: if true`) since it's shown pre-auth on signup pages and the public quote-request form, owner-only to write.

**These are the only pages in the app that work as real, cold, external links — everything else doesn't.** `MaterialApp.home` in `frontend/lib/app.dart` always resolved to `_SessionGate` (dashboard-or-login based on Firebase Auth state) regardless of the URL, and `onGenerateRoute` only ever runs on an in-app `Navigator` push, never on the initial page load — so historically no deep link in this app worked from outside the running app (confirmed by testing `/equipment/detail`-style paths). `_resolveInitialHome()` in `app.dart` is a narrow, deliberate carve-out: on startup it checks `Uri.base.path` and, when it equals `AppRouter.legalDocument`, renders `LegalDocumentPage` directly (reading `documentId` from `Uri.base.queryParameters`, not route `arguments`) instead of `_SessionGate`; when it equals `AppRouter.clientSignup`, it renders `ClientSignupPage` directly, no login screen first — every other route is untouched and still only reachable from inside the app. The legal-document carve-out exists because the Privacy Policy/Terms links needed to actually work when pasted into Twilio's A2P 10DLC campaign registration form (see "Third-party service live status" below) — the URL shape is `https://anchor-orpin.vercel.app/legal/document?documentId=privacy_policy` (also `terms_of_service`, `employee_data_notice`). The client-signup carve-out was added 2026-09-03 after Twilio **rejected** that same campaign for an unverifiable Call to Action: a reviewer hitting `https://anchor-orpin.vercel.app/signup/client` directly (rather than clicking through from the login page, which does work — in-app `Navigator` pushes fire `onGenerateRoute` normally once the SPA is already loaded) fell through to a bare login screen instead of the actual signup form with the SMS-consent language, since only `/legal/document` had this carve-out at the time — confirmed live by hitting that exact URL before and after the fix. If a future feature needs another page to be a real external link (App Store listing, ad platform, etc.), extend `_resolveInitialHome()` the same way rather than assuming `onGenerateRoute` alone will handle it.

**Static, JS-free mirrors for automated verification** (added 2026-09-03, after a third A2P rejection with the same "a compliant privacy policy can not be verified" reason): even with the `/legal/document?documentId=...` cold-link carve-out above making the *app* reachable pre-auth, the page is still a Flutter web SPA — `curl`'ing that URL returns nothing but the generic `web/index.html` shell (`<title>Anchor</title>`, `<meta name="description" content="A new Flutter project.">`, a `<script src="flutter_bootstrap.js">`, zero page text) until JS boots the CanvasKit-rendered app client-side. Confirmed live: a plain `curl` of the privacy-policy URL had no occurrence of "Privacy Policy," "Ryan Prendergast," or "RP Landscaping" anywhere in the response. Any compliance scraper that doesn't run a full JS engine (or times out before Flutter's WASM bundle finishes booting) sees an effectively blank, unbranded page — a very plausible reason all three rejections cited an unverifiable privacy policy even after the brand-name-match content fix. The fix: `frontend/web/legal/{privacy-policy,terms-of-service,employee-data-notice}.html` are plain, dependency-free static HTML files (real `<title>`/`<meta description>`, inline `<style>`, no JS) checked directly into `frontend/web/` (Flutter's web build copies that whole directory into `build/web/` verbatim) — Vercel's catch-all SPA rewrite (`/(.*) → /index.html` in the root `vercel.json`) only fires when no static file matches the request path, so `/legal/privacy-policy.html` etc. are served as literal files, bypassing the SPA entirely (the same precedence the app already relies on for its own `main.dart.js`/`flutter_bootstrap.js` to load at all). These are a **manual content snapshot**, generated once from the live `legal_documents` Firestore content (same relationship as `docs/legal/*.txt` above) — they will drift if the owner edits a document in-app afterward and nobody regenerates them; there's no live sync. The in-app `/legal/document?documentId=...` route and every in-app "Privacy Policy"/"Terms of Service" link are unaffected and still show the real-time Firestore content — these static files exist solely as an additional, crawlable target for third parties (Twilio A2P registration and anything similar in the future) and were submitted to Twilio in place of the SPA URLs.

**The rest of the crawlability surface (added 2026-09-04, after a *fourth* rejection with the same error).** Making the three legal documents crawlable was necessary but not sufficient — three more JS/routing gaps were found by actually fetching things, and all three are fixed now:
- **`frontend/web/index.html` now carries a `<noscript>` block** with the business identity ("Ryan Prendergast, doing business as RP Landscaping"), the SMS opt-in disclosure verbatim, the STOP/HELP language, the no-mobile-data-sharing sentence, and links to all four static legal pages. This matters because the **client sign-up page is the URL named in the campaign's `message_flow` as the point of consent**, and `curl https://anchor-orpin.vercel.app/signup/client` returned a 1729-byte Flutter shell with `<title>Anchor</title>` and *zero* occurrences of "privacy," "consent," or the consent sentence — the static legal mirrors did nothing for it, since `/signup/client` is a live interactive form and can't be replaced by a static file. Every SPA route's raw HTML now contains that text. The `<meta name="description">` was still Flutter's stock `"A new Flutter project."` and is now a real description. Keep the consent sentence in the `<noscript>` block byte-identical to the one in `client_signup_page.dart` (it is currently *below* the phone field, not above — the registered `message_flow` text said "above," which was simply wrong and is the kind of detail a reviewer checks).
- **`frontend/web/legal/sms-consent.html`** is a new fourth static page (no Firestore doc behind it — deliberately, it documents the app's opt-in *mechanics*, not owner-editable policy wording) describing the whole opt-in flow, the message categories, sample messages, and opt-out, in plain HTML. It's the page to hand a carrier/compliance reviewer who wants to see the consent flow without running the app.
- **`vercel.json` gained a `redirects` block, and `frontend/web/robots.txt` now exists.** The root rewrite (`/(.*) → /index.html`) means *every* unmatched path returns **HTTP 200 with the blank SPA shell** rather than a 404 — which turned a one-character typo into a silent failure: the registered `message_flow` ended each URL with a sentence period (`...privacy-policy.html.`), and any URL extractor that grabs the trailing dot fetched `https://anchor-orpin.vercel.app/legal/privacy-policy.html.` and got **200 OK plus a blank page**, i.e. exactly "a compliant privacy policy can not be verified." The redirects strip a trailing dot on all four legal paths and also alias `/privacy`, `/privacy-policy`, `/terms`, `/terms-of-service`, `/sms-consent` and the extensionless `/legal/<name>` forms to the real files. `robots.txt` exists for the same reason — it used to fall through the rewrite and get served as HTML with a 200. **If you ever add another externally-registered URL, `curl` the exact string that was registered, trailing punctuation included, and confirm real content comes back — a 200 here proves nothing.**

Surfaced everywhere account creation or PII collection happens: a required "I agree to the Privacy Policy and Terms of Service" checkbox (employee signup instead links Terms of Service + the Employee Data Privacy Notice) on `client_signup_page.dart`, `employee_signup_page.dart`, and `claim_account_page.dart` (all three create a real Firebase Auth account); an SMS-consent line next to the phone field on client signup (the only account-creation flow where a phone number triggers text reminders); a non-blocking Privacy Policy link on the public `request_form_page.dart` (pre-auth lead capture, lower friction than a checkbox); a `Privacy Policy · Terms of Service` footer on `login_page.dart`; and links to the relevant documents inside Client/Employee/Owner Settings (`app_scaffold.dart`'s three settings dialogs) — the owner's settings link goes straight to the admin edit page instead of the read-only viewer, since they're the one who owns the wording.

**Self-service account deletion** (new capability, not just documentation): Client and Employee Settings each got a "Request Account Deletion" button (`_requestAccountDeletion` in `app_scaffold.dart`) — it does **not** delete anything itself, it files an in-app `AppNotification` (`type: NotificationType.deletionRequest`) to the owner, who still handles the actual deletion manually via the existing owner-only `ClientProfileService.deleteClientPermanently` (which already refuses to delete a client with any invoices/estimates/jobs on file) or by deactivating an employee — there was no equivalent employee-deletion flow before this and still isn't; only a notification. This required a narrow, explicitly-scoped addition to `notifications`' `create` rule in `firestore.rules`: a signed-in non-owner can create a notification *only* if it targets `recipientRole: 'owner'` with `type: 'deletionRequest'` and the standard field set — every other notification type/recipient still requires `isOwner()`, so this can't be repurposed to spoof other notifications.

### Auth model — real identity, real Firestore rules, for all three roles
**As of 2026-09-01, all three roles use real Firebase Auth, and `firestore.rules` actually enforces role- and identity-scoped access on every collection** (previously: hardcoded owner password, client/employee SHA-256-in-Firestore, and `allow read, write: if true` almost everywhere). Read this before touching login, signup, any `*_service.dart` query/write, or `firestore.rules`:

- **Identity**: a Firebase Auth account per user (email/password for all three roles — no Google Sign-In in the live app; `FirebaseService`/`google_sign_in` were dead code and have been deleted). Two **custom claims** are the source of truth, set *only* server-side, never trust a client-supplied value:
  - `role` (`owner`/`employee`/`client`) — what someone is.
  - `profile_id` (client/employee only) — the caller's own `client_signups`/`employee_signups` **doc id**. This exists because those two collections are the only ones with a real `uid` field; every other collection (`estimates`, `invoices`, `scheduled_work`, `client_messages`, `notifications`, `time_entries`, `employee_availability`, …) identifies "whose record is this" by that old doc id, not `uid` — `firestore.rules` compares `resource.data.clientId`/`employeeId` against `request.auth.token.profile_id` to scope a session to its own records, rather than requiring a data migration of every document to store `uid` instead.
- **Who can become what**: `POST /auth/complete-signup` (`backend/app/api/v1/routes/auth.py`) is the only place a role (and `profile_id`) gets granted, given an already-verified Firebase ID token. `owner` requires the caller's email to be in `settings.owner_emails` (`OWNER_EMAILS_RAW` env var, currently just `immc17289@gmail.com`, and gets no `profile_id` — owner-only rules just check `role`); `employee` requires a real `invite_codes` entry; `client` is unconditional. `POST /auth/claim-account` is the separate pre-auth flow for turning an owner-created "dummy" client (`ClientProfileService.createDummyClient`, no email/password yet) into a real login via a one-time claim code — it creates the Firebase user itself since no one is signed in yet at that point.
- **Frontend**: `login_page.dart`/`owner_signin_page.dart` use `FirebaseAuth.instance.signIn/createUserWithEmailAndPassword` directly; the app's real entry point is `_SessionGate` in `frontend/lib/app.dart`, which now reacts to `FirebaseAuth.instance.authStateChanges()` (reading the `role` claim off a fresh ID token, then loading the matching profile) instead of a local-storage session blob — `SessionPersistenceService` is gone, Firebase's own SDK persistence replaced it. `ClientProfileService.fetchByUid`/`EmployeeProfileService.fetchByUid` (query by a `uid` field, not the doc ID — existing docs keep their old IDs, only new field added) are how a profile gets resolved from a signed-in Firebase user. `client_signup_page.dart`/`employee_signup_page.dart` force a **second** `getIdToken(true)` refresh after `/auth/complete-signup` returns, before navigating to the dashboard — the first token (fetched pre-signup) predates the claims `/auth/complete-signup` just set, and reusing it caused one `permission-denied` on the very first dashboard load. `_SessionGate` itself retries its own role check up to 5 times (600ms apart) before concluding an account is genuinely orphaned and signing it out — `authStateChanges()` fires the instant `createUserWithEmailAndPassword` succeeds, racing the signup page's own subsequent `/auth/complete-signup` call, and without the retry a real, successful, in-progress signup would very reliably (not just occasionally) get bounced straight back to login, since `_SessionGate`'s check almost always lost that race. A separate, less deterministic token-propagation lag is still observed on ordinary (non-signup) first writes — e.g. an employee's very first clock-in right after landing on the dashboard can fail once with `permission-denied` even though the same write succeeds immediately via a direct REST call with the same token, proving it's the Firestore Web SDK's own internal credential caching lagging behind the ID token, not a rules problem. Not yet root-caused or fixed; if it recurs, look at Firestore Web SDK auth-state propagation, not the rules themselves — and don't "fix" it by loosening a rule, since a raw REST call with the identical token already proves the rule is correct.
- **Migration** (one-off, already run against production): `backend/scripts/migrate_existing_accounts.py` created a Firebase Auth account + `role` claim for every pre-existing `client_signups`/`employee_signups` doc that had a real `password_hash` (dummy/unclaimed clients were left untouched — they still go through claim-account), stripped `password_hash`, and generated (but didn't send) a password-reset link per account; `backend/scripts/send_reset_emails.py` is the separate, deliberately-manual step that actually emails those links. `backend/scripts/backfill_profile_id_claims.py` (also one-off, already run) is the equivalent backfill for the `profile_id` claim — needed once, since accounts migrated before `profile_id` existed only had `role` set.

**`firestore.rules` design** (see the file itself for the exact per-collection logic): owner gets unrestricted access everywhere. Client/employee-scoped collections (`estimates`, `invoices`, `scheduled_work`, `client_messages`, `notifications`) check `resource.data.clientId`/`targetClientId`/`recipientId` against the caller's `profile_id` claim; a client can additionally write `status`/`changeRequestMessage` on their own estimate (approve / request changes — the only writes the client UI performs) but nothing else — this is also value-restricted (`status` must be `'approved'` or `'changes_requested'`, not just field-restricted), since field-restriction alone would still let a client write any string into `status`. `time_entries`/`employee_availability` are employee-self-scoped by `profile_id` too (new write-integrity protection — previously nothing stopped one employee's session from editing another's hours or availability); `time_entries` additionally restricts which *fields* an employee's own write can touch (`clockInAt`/`clockOutAt`/etc. only) — `wageOverride`/`isPaid`/`notes` stay owner-only, since matching on `employeeId` alone doesn't stop an employee from setting those on their own doc via the raw SDK. `equipment`/`equipment_reservations`/`equipment_baskets`/`equipment_kits`/`broken_reports`/`service_records`/`job_completion_forms`/`teams` are staff-shared (owner + employee, no per-employee scoping — this codifies the app's existing "full parity" design, not a new restriction). `expenses`/`service_catalog`/`checklist_templates`/`invite_codes` are owner-only. `owner_settings` stays publicly readable (branding is used on the pre-auth lead form and on both owner- and client-facing PDFs) but owner-only to write; `legal_documents` is the same shape (publicly readable, owner-only write) for the same pre-auth-visibility reason. `requests` allows public `create` (the pre-auth "Request a Quote" form) but staff-only read/update. `notifications`' `create` rule has one narrow carve-out beyond `isOwner()` — a signed-in client/employee can create *only* an owner-targeted, `type: 'deletionRequest'` notification with the standard field set (see "Legal documents" above), not any other notification shape. Because several pages (`messages_page.dart`, `estimates_page.dart`, `invoices_page.dart`, `appointments_page.dart`) used to call `ClientProfileService.watchAllProfiles()` (the full, unscoped client directory) unconditionally regardless of role just to resolve a display name, those call sites were changed to skip that subscription (or substitute the caller's own already-known profile) for client-role sessions; `dashboard_page.dart`'s `ReminderCheckService.checkAndCreateReminders()` call — inherently business-wide (scans every client's invoices/appointments) — is now gated to `role == 'owner'` only instead of firing for every role on every dashboard load. `storage.rules` (not live — see Deploy above) got the same real-role treatment even though it's currently inert, so it doesn't silently reopen a hole whenever Storage is ever provisioned.

**`/comms/*` and `/photos/upload`: what's actually allowed pre-auth.** These two routes are genuinely reachable before login — `request_form_page.dart` (the public "Request a Quote" form) emails a confirmation to whoever just submitted it and lets them attach photos, all before any account exists — so neither route could simply require authentication across the board.
- **`POST /comms/email`** (`backend/app/api/v1/routes/comms.py`) takes `{to, template, params}`, never raw `subject`/`html_body` — the actual content (subject + HTML-with-placeholders) lives server-side in `backend/app/services/email_service.py`'s `_TEMPLATES` dict, and every param gets HTML-escaped before interpolation. This is what closes the real hole a caller-supplied-content route had: even the two pre-auth templates (`request-confirmation`, `owner-new-lead`) can't be used to send arbitrary HTML/phishing content to an arbitrary address, since content is fixed regardless of auth state. `appointment-reminder`/`invoice-reminder` additionally require a real owner bearer token (checked inline via `_require_owner()`, which verifies the Firebase custom claim directly rather than going through a `users`-collection lookup — deliberately, to avoid a fallback-to-CLIENT-role edge case for a security-relevant check; see the `deps/auth.py` note below). `EmailService.send_email(to, subject, html_body)` — the old free-form method — still exists and is still used by one-off scripts (`backend/scripts/send_reset_emails.py`) that call it directly via Python import, never through the HTTP route; that's fine, since those scripts run with real credentials on a developer's own machine, not from an untrusted caller.
- **`POST /comms/sms`** always requires an owner bearer token — there's no pre-auth caller for it (only `reminder_check_service.dart`, itself owner-gated). `to` must match E.164 format (`SmsSendRequest` in `schemas/comms.py`).
- **`POST /photos/upload`** (`backend/app/api/v1/routes/photos.py`) allows an unauthenticated call only when `folder` starts with `request_photos/` (the exact prefix `JobPhotoUploadService.pickAndUploadRequestPhoto` uses); any other folder (`job_photos/*`, `equipment_photos/*`) requires a bearer token, and `job_photo_upload_service.dart`'s other two upload methods now attach one (`FirebaseAuth.instance.currentUser?.getIdToken()`). Content-Type is no longer trusted as a label — `_validate_real_image()` actually decodes the bytes via Pillow (`Image.open(...).verify()`) before it's forwarded to Cloudinary, so a spoofed `Content-Type: image/svg+xml` carrying a script payload can't pass as a real image anymore.
- Both routes' rate limits assume `request.client.host` reflects the real caller IP, not Cloud Run's own proxy — that only works because the Dockerfile's `CMD` passes `--proxy-headers --forwarded-allow-ips='*'` to uvicorn (safe specifically because Cloud Run's ingress means the container is never reachable except through Google's proxy). Don't remove that flag without understanding this — without it, slowapi's per-IP limiting either bucket-limits every caller together or doesn't limit anyone meaningfully.
- `backend/app/core/middleware.py`'s `MaxBodySizeMiddleware` rejects by `Content-Length` before a route runs (256KB default, 11MB for `/photos/upload`) — a floor under the per-field `max_length`s already in the Pydantic schemas, not the primary control.
- `/docs`, `/redoc`, `/openapi.json` are disabled unconditionally (`FastAPI(docs_url=None, redoc_url=None, openapi_url=None)` in `main.py`) — no interactive API explorer in production, on principle, for an API with exactly one real frontend.

**What's still NOT covered** — don't assume otherwise:
- `DEV_AUTH_BYPASS`: the `core/config.py` setting and its Phase 0 startup guard (`_forbid_dev_bypass_against_real_firestore`, refusing to boot if it's ever combined with `USE_MOCK_FIRESTORE=false`) still exist, but the code that actually consumed it — `get_current_user`'s `dev-owner`/`dev-employee`/`dev-client` fake-token branch, in `api/deps/auth.py` — was deleted as dead code (nothing called `get_current_user` any more; `/comms`/`/photos` check auth inline instead, see above, and no other route ever used it). So the flag is currently inert: setting it does nothing, since nothing reads it besides that startup guard. If local/mock-Firestore dev ever needs a fake-auth shortcut again, it'd need to be rebuilt somewhere an actual route reads it.

### Backend layering
Standard layered FastAPI structure: `api/v1/routes/*.py` (request/response, now just `auth.py`/`comms.py`/`photos.py`) → `services/*.py` (business logic) → `repositories/firestore_repository.py` (generic Firestore CRUD, with an in-memory dict fallback when `USE_MOCK_FIRESTORE=true`, used only by `users_service.py` today) → `schemas/*.py` (pydantic models). `core/config.py` (`Settings`, env-driven, see Auth model above for the dev-bypass guard), `core/firebase.py` (lazy Firebase Admin init, supports both a checked-in `service-account.json` and a base64 env var for Cloud Run — `require_firebase_app()` is the version every route actually calls, which turns any init failure into a generic `HTTPException` and logs the real exception server-side only, rather than each route inlining its own try/except that leaked the local `service-account.json` filename convention to the caller), `core/rate_limit.py` (the shared `slowapi` `Limiter` instance), and `core/middleware.py` (`MaxBodySizeMiddleware`, see "Comms & photos" under Auth model) are shared across routes. CORS (`main.py`) allows `settings.allowed_origins` plus, only when `ALLOW_LOCALHOST_CORS=true` (local dev only — never set on Cloud Run, so production never allows a localhost `Origin`), any `localhost`/`127.0.0.1` port.

### Frontend layering
`lib/features/<feature>/presentation/*.dart` (pages/widgets) → `lib/core/services/*.dart` (data access — Firestore directly or `ApiClient`, per feature) → `lib/models/*.dart` (plain Dart model classes with `fromMap`/`toMap`/`fromJson`). Routing is a single `switch` in `lib/core/router/app_router.dart` (`AppRouter.onGenerateRoute`); role and `authToken` are passed as route arguments (a `Map<String, dynamic>`) on every in-app navigation call, so an individual page's "current role" is whatever the caller happened to pass — `_SessionGate` (see Auth model) is the one place that derives role from the real, global Firebase Auth state (on app boot / auth state change), then threads it into the first route args the same way. **`onGenerateRoute` only ever fires on an in-app `Navigator` push — never on a cold page load**, so no route in this app is a real, externally-shareable link by default (`MaterialApp.home` always resolves to `_SessionGate`, ignoring the URL); the deliberate exceptions are `/legal/document` and `/signup/client`, handled by `_resolveInitialHome()` in `app.dart` — see "Legal documents" above. Global mutable session state (`ClientSession`, `EmployeeSession`, `OwnerSession` in `lib/core/state/`) is `ValueNotifier`-based and used for cross-cutting concerns like the notification listeners in `app.dart`, separate from the per-route role/token arguments.

Platform-conditional code (CSV/PDF download, Google Calendar embedding) is split into `_io.dart`/`_web.dart`/`_stub.dart` variants per service (e.g. `csv_download_service_web.dart` vs `_io.dart`) selected via conditional imports from the non-suffixed file — follow that pattern for anything else that needs to behave differently on web vs. native.
